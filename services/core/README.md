# API Документация сервиса управления расписанием и пользователями

## Введение

Сервис предоставляет REST API для управления пользователями, ролями (администратор, менеджер, преподаватель, студент, пользователь), группами, аудиториями и учебными предметами. Аутентификация осуществляется с помощью JWT токенов. Все эндпоинты, кроме `/login` и `/refresh`, требуют передачи JWT токена в заголовке `Authorization: Bearer <token>`.

## Общая информация

- **Базовый URL**: `http://<host>:<port>` (по умолчанию порт `8080`)
- **Формат ответов**: JSON
- **Структура ответа**:
  - Успешный ответ:
    ```json
    {
      "success": true,
      "message": "string",
      "data": { ... } // может отсутствовать
    }
    ```
  - Ответ с ошибкой:
    ```json
    {
      "success": false,
      "error": "string"
    }
    ```
- **Аутентификация**: JWT токен передается в заголовке `Authorization: Bearer <access_token>`
- **Роли**:
  - `admin` – полный доступ ко всем админским операциям
  - `manager` – управление ролями (назначает/удаляет роли `admin`, `manager`)
  - `teacher` – преподаватель (профиль)
  - `student` – студент (профиль с привязкой к группе)
  - `user` – базовая роль, присваивается при регистрации

## Эндпоинты

### Аутентификация

#### POST `/login`
Вход в систему, получение токенов доступа и обновления.

**Тело запроса**:
```json
{
  "username": "string",  // обязательное, от 3 до 20 символов, только буквы, цифры, _
  "password": "string",  // обязательное
  "user_agent": "string", // опционально, будет заполнено из заголовка User-Agent
  "client_ip": "string"   // опционально, будет заполнено из X-Forwarded-For или RemoteAddr
}
```

**Успешный ответ (200 OK)**:
```json
{
  "success": true,
  "message": "success login",
  "data": {
    "access_token": "string",
    "refresh_token": "string",
    "session_id": "string",
	"roles": ["string"]  // список ролей
  }
}
```

**Ошибки**:
- 400 – неверный формат запроса или ошибка валидации
- 400 – неверное имя пользователя или пароль

#### POST `/refresh`
Обновление access-токена с использованием refresh-токена.

**Тело запроса**:
```json
{
  "session_id": "string",   // обязательное
  "refresh_token": "string" // обязательное
}
```

**Успешный ответ (200 OK)**:
```json
{
  "success": true,
  "message": "success refresh token",
  "data": {
    "access_token": "string",
    "refresh_token": "string"
  }
}
```

**Ошибки**:
- 400 – неверный формат запроса или ошибка валидации
- 500 – внутренняя ошибка сервера

#### GET `/logout`
Выход из системы (удаление сессии). Требует валидный access-токен.

**Успешный ответ (200 OK)**:
```json
{
  "success": true,
  "message": "success logout",
  "data": null
}
```

**Ошибки**:
- 401 – невалидный токен
- 500 – внутренняя ошибка сервера

Получить список всех активных сессий.

**Успешный ответ (200 OK)**:

**Ошибки**:

#### Управление пользователями

##### GET `/admin/users`
Получить список пользователей с пагинацией.

**Параметры запроса (query)**:
- `page` (int, опционально, по умолчанию 1) – номер страницы
- `per_page` (int, опционально, по умолчанию 20) – количество записей на странице
- `sort_by` (string, опционально, по умолчанию `id`) – поле для сортировки: `id`, `username`, `full_name`, `email`, `created_at`
- `sort_order` (string, опционально, по умолчанию `ASC`) – порядок сортировки: `ASC` или `DESC`

**Успешный ответ (200 OK)**:
```json
{
  "success": true,
  "message": "paginated users",
  "data": {
    "users": [ ... ],      // массив объектов User (см. модель)
    "total": 100,
    "page": 1,
    "per_page": 20,
    "total_pages": 5
  }
}
```

##### GET `/admin/users/{id}`
Получить информацию о пользователе по его ID.

**Параметры пути**:
- `id` (int) – идентификатор пользователя

**Успешный ответ (200 OK)**:
```json
{
  "success": true,
  "message": "get user success",
  "data": { ... } // объект User
}
```

**Ошибки**:
- 400 – неверный ID
- 404 – пользователь не найден
- 500 – внутренняя ошибка сервера

##### POST `/admin/users`
Создание нового пользователя (без профиля студента/преподавателя). Пользователю автоматически присваивается роль `user`.

**Тело запроса**:
```json
{
  "username": "string",   // обязательное, 3-20 символов, буквы/цифры/_
  "full_name": "string",  // обязательное, минимум 3 символа
  "email": "string",      // обязательное, валидный email
  "password": "string"    // обязательное, минимум 6 символов
}
```

**Успешный ответ (201 Created)**:
```json
{
  "success": true,
  "message": "user created",
  "data": { ... } // объект User
}
```

**Ошибки**:
- 400 – ошибка валидации или конфликт (уже существует)
- 500 – внутренняя ошибка сервера

##### PATCH `/admin/users/password`
Смена пароля пользователя (администратором). Администратор может сменить пароль любому пользователю, указав `user_id`. Если `user_id` не указан, считается, что смена пароля для текущего пользователя (но в этом случае используется эндпоинт `/user/password`).

**Тело запроса**:
```json
{
  "user_id": 123,          // обязательное, если администратор меняет пароль другому пользователю
  "new_password": "string" // обязательное, минимум 6 символов
}
```

**Успешный ответ (200 OK)**:
```json
{
  "success": true,
  "message": "password changed",
  "data": null
}
```

**Ошибки**:
- 400 – неверные данные
- 403 – доступ запрещен (не admin или попытка смены чужого пароля без прав)
- 500 – внутренняя ошибка сервера

## Коды ответов

- `200 OK` – успешное выполнение запроса
- `201 Created` – ресурс создан (используется для создания пользователя)
- `400 Bad Request` – неверный запрос (ошибка валидации, неправильный формат)
- `401 Unauthorized` – отсутствует или невалидный JWT токен
- `403 Forbidden` – доступ запрещен (недостаточно прав)
- `404 Not Found` – ресурс не найден
- `500 Internal Server Error` – внутренняя ошибка сервера
